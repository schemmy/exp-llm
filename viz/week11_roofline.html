一次 batch sweep（1→512），四件事共用同一根轴——算术强度。 这张图把 CUDA graph、脊点预测、MFU/MBU、还有 FP8/INT8 量化的胜负， 全部叠进同一个坐标系看。

01

Roofline：吞吐撞上算力天花板的地方

横轴是算术强度（对 decode 这种权重固定型 GEMM，它恰好等于 batch size）。 纵轴是实际算力（TFLOPS）。两条细线是 A100 的理论上限—— 带宽线和 算力线相交的地方就是理论脊点 M≈153。 两条粗虚线是这套系统实际能摸到的天花板（约 72% MBU、约 52% MFU）—— 紫色的实测点几乎贴着它走。

怎么读这张图

紫色点从 batch=1 开始几乎贴着蓝色虚线（带宽天花板）往右上爬—— 这段是免费的：多算的 token 不需要多搬权重。

过了 batch≈128，点开始脱离蓝线、转向橙色虚线（算力天花板）靠拢， 到 batch=256 基本贴住，batch=512 时紧贴着橙线甚至轻微下滑—— 这就是"加 batch 已经不再有任何帮助"的视觉证据。

两条虚线都在理论线下方——真实硬件从来摸不到 100%， 这个约 20-50% 的落差本身就是这周最该记住的数字之一。

02

CUDA Graph：固定开销，随 batch 被摊薄

横轴和上图对齐（同样是 batch）。纵轴是 graph / eager 的吞吐比。 launch 开销和 Python 分发开销是每步固定的，batch 越大、每步计算越多， 这部分固定成本占比就越小——所以收益曲线单调下降。

graph 相对 eager 的加速比 1.0x（无收益基线）

预测被打脸的地方

原估算：launch 开销约 300-400 次 × 5-10µs ≈ 2ms，TPOT 10.3ms 里占约 20%， 预期收益 ~1.2x。

实测 batch=1 是 2.69x——差了一个数量级。漏算的是 PyTorch eager 模式下 Python 分发层的开销，这部分通常比纯 CUDA launch 大一个数量级， CUDA graph 把这两层都省掉了。

两条量化路线，两种命运

FP8 的加速比精确在 batch=32 → batch=256 之间翻脸（1.51x → 0.84x）， 正好卡在上面 roofline 图测出的转折区间（128-256）——省字节在带宽区能兑现， 在算力区只剩反量化的纯支出。

INT8（int8_per_channel_weight_only）三个点全部趴在 1.0x 附近， 连"净亏"的资格都没混上，因为它压根没赚到过。同样是"减字节"， 没有高效 kernel 路径承接就只是数字游戏——这是本周最反直觉的一条。
